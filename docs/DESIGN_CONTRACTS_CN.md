# 叙事与设计约束

## 1. 事实状态
所有设定、剧情和结局提案必须带状态：
- **已确认**：用户明确认可，可作为后续设计的约束。
- **提案**：助手或用户提出、尚未定稿的方案。
- **待解决**：存在冲突或信息不足，暂不推断。
不要把提案悄悄写进正式剧情文档当作事实。

## 2. 两款游戏的边界
- 《蜜忒之歌》：蜜忒视角的生活、关系、探索、推理与世界异变。
- 《Nereis-Hero》：Hero 视角的动作探索 RPG，属于另一个项目。
- 共享已确认的世界事实，但允许视角、信息量和解释不同。
- 任何跨游戏衔接必须满足时间线、人物认知、事件因果一致；不要求两款游戏采用同一条主线。
- 不得擅自确定 Hero 的后续命运、复国军结局或蜜忒的最终命运。

## 3. 视角与 UI 文案
- 游戏主要采用蜜忒的第一人称体验；涉及玩家自身的住所、行动、观察和感受时，优先使用自然的第一人称表达，例如“我家附近”“我来到了这里”。
- 不要把蜜忒当作外部角色称呼（例如“蜜忒家附近”），也不要在玩家操作界面中用旁观者口吻描述她。
- 地图地点、NPC 名称和客观记录可以使用中性名称；不要为了第一人称而把所有标签都机械改成“我”。
- 线索簿服务于玩家推理，但文字应符合蜜忒当下的认知，不可替她揭示她尚不知道的真相。

## 4. 角色认知约束
始终区分：
1. 玩家掌握的信息；
2. 蜜忒在当前时间点真实相信的信息；
3. 世界中的客观事实；
4. 其他角色各自知道、误解或遗忘的信息。
角色不能因为玩家发现线索就自动知道真相。记忆异常必须有一致规则和可追溯线索。

## 5. 关系与结局的独立性
- 关系系统可影响私人剧情、陪伴、对话和角色反应。
- 调查系统可影响线索、世界认知和事件解锁。
- 主要结局条件不能简单等同于好感度。
- 身体结合或某个亲密事件不能成为 RPG 主要结局的硬门槛；本项目也不应默认采用这种硬门槛。
- 关系与世界状态可以互动，但每条因果链必须明确并可测试。

## 6. 日常模拟与仪式
- 日常行为必须同时作为可理解的生活行为成立；不能每个动作都只为隐藏数值服务。
- 蜜忒的情感和善意应当真实。
- 村民应有各自的日程、关系、记忆和压力反应；不是全员同一意识的复制品。
- 关键异变由明确事件触发；隐藏状态可以影响准备条件、表现和可见线索，不要只靠一个腐化值自动切换世界。
- 重要剧情可以错过现场，但应尽可能提供可追溯的后续证据，避免无提示软锁。

## 7. 玩家体验
- 自由活动要有意义的反馈：关系、线索、地点、资源、旧事件的新解释或延迟后果。
- 不要把游戏做成每天机械打卡的日程表。
- 玩家可以错过支线，但避免因为错过一次日常行动就永久封锁主线理解或主要结局。
- 先实现小型垂直切片，验证核心循环，再扩展规模。

## 8. 文档和仓库纪律
- 中英文文档同步更新。
- 每次新对话先阅读 `SESSION_START_HERE`、`WORLDVIEW`、`DESIGN_CONTRACTS`、`CORE_GAMEPLAY`、`ROADMAP`。
- 不触发 GitHub Actions。
- 报告必须区分静态检查、逻辑模拟、引擎运行和人工游玩验收。
